# CITY LIFT — Blender切断経路の実現性スパイク（Issue #6）

## 結論

**推奨は条件付きGo：実装・データ取得はまだ行わず、LIFT-LITEの目視判定で着手順を決める。** 最小検証は「千代田区1km四方、白素材、切断1回、静止画1枚」。CityGMLからの取り込みと断面生成の実動可否は**要検証**。今回は文書のみで、インストール・データ本体の取得・レンダーは行っていない。

[EXP-001](../experiments/EXP-001.md)では、LITEの技術評価はテスト・ビルドPASS、クリエイティブ評価は**未確認**。画像を見ずにBlender経路の魅力や成功を判定しない。LITEが浮遊模型に見えるなら断面は仕上げとして後順位、浮遊に見えないなら断面を欠けた要素という仮説で優先検証する。

## 目的とNavara側の限界

真のCITY LIFTは、PLATEAUの実在都市から矩形または円形の地区を切り出し、厚みのある断面（地層風の側面）を見せて浮かべる表現。建物を暗背景へ置くだけのLITEとの差は、街を一つの「物体」にする縁・側面・底面にある。

EXP-001の既存調査ではNavara/3D Tilesはストリーミング描画で、任意境界での幾何クリッピング、切断面生成、地形ごとの持ち上げは標準機能にない。表示のクリップだけでは閉じた側面・底面は得られないため、オフラインでメッシュを加工する設計とする。Navaraの最新API・内部実装の再調査は未実施（**要検証**）。

## データ経路とHEAD確認

対象は**東京都千代田区の2023年度（FY2023）CityGML**。比較候補は同年度の新宿区。既存の2023年3D Tiles URLの実証と、CityGML原本の配布確認は分ける。

- 配布探索の入口：[国土交通省PLATEAUポータル](https://www.mlit.go.jp/plateau/)、[G空間情報センター](https://www.geospatial.jp/)。ここから東京都23区・2023年度のデータセットを探し、千代田区／新宿区のCityGMLリソースを選ぶ設計。該当年度・区の現行掲載状況は**要検証**。
- 想定形式はCityGML一式を格納したZIP。区別／メッシュ別の分割、LOD、建物・地形・道路の収録範囲、ZIPサイズと展開容量はすべて**要検証**。地形が建物と同じZIPに含まれるとは仮定しない。
- 2026-11-05、ポータルとG空間の候補URL `https://www.geospatial.jp/ckan/dataset/plateau-tokyo23ku-2023` に `curl -I -L --max-time 15` を実行。両方ともプロキシ `hatch-egress-proxy:3128` への接続失敗（curl終了コード7）でHTTP応答なし。候補URLの実在、到達性、配布形式、容量は**未確認・要検証**。ZIP直リンクは特定できていない。
- 到達可能な環境では、公式カタログで特定したZIP直リンクにHEADのみ実行し、リダイレクト先、HTTP状態、`Content-Length`、`Content-Type`、`Content-Disposition` を記録する。HTMLのサイズをZIPサイズと誤認しない。HEAD非対応・長さ省略なら「容量不明」とし、GETやRange取得で代替しない。
- HEADはヘッダーによる形式の推定まで。ZIP内部のCityGML・対象区・LOD・利用条件の確証は別途取得後の検査が必要（**要検証**）。出力には原典・年度を表示し、人工の地層側面を実測地下地質と区別する。

## 取り込み経路の比較

以下は設計候補。ネットワーク制約によりリポジトリ、リリース、対応Blender版の現況は確認できておらず、**全候補の保守状況は要検証**。特定アドオンの存在や現行互換性を保証しない。

| 候補 | 経路と利点 | リスク・採否条件（要検証） |
| --- | --- | --- |
| A：CityJSON経由（第一候補） | CityGML → CityJSON変換（例：citygml-tools系）→ CityJSON対応Blenderインポーター。変換と描画を分離して原因を追う設計 | PLATEAU拡張・LOD2・座標系への対応、穴付き面の三角形化、属性保持、変換器／インポーター双方の保守状況は要検証。小メッシュで通れば採用 |
| B：CityGML直接取り込み | plateau-blender-importer型のアドオンで直接メッシュ化。中間形式を減らす候補 | 具体的な採用実装、公開元、ライセンス、更新日、Blender Python API互換性、大規模データ耐性は要検証。名称だけで採用せず、再現できる版を固定できた場合に限定 |
| C：OBJ経由（代替） | オープンなCityGML変換ツール（例：市街地モデル用の三角形化・OBJ出力系）→ Blender標準OBJ取り込みを狙う。FME不要 | 実際にPLATEAUを読めるツールと出力機能、保守状況は要検証。CRS・意味属性が失われる前提で別途レシピに保存。FBXはオープンな書き出し対応まで未確認（要検証）のため初手にしない |

Aが失敗したらB/Cのうち小メッシュで再現できる経路へ切り替える。複数経路の同時構築はせず、取り込み調査の上限を4人時とする提案。

## パイプライン設計

1. **抽出・座標整備**：千代田区内の1km四方を定義し、必要メッシュだけ処理する。メートル単位の投影座標へそろえ、地区中心をローカル原点へ移す。CRS、軸、標高基準、境界座標、入力ハッシュを記録。実データのCRS・変換精度は**要検証**。
2. **メッシュ化**：候補Aから開始。白素材で建物の高さ・位置・欠落・法線を確認する。道路や実地形の取り込みは最小検証の必須条件にせず、未収録なら人工台座を明示する。
3. **切断**：矩形の境界ボックスとBoolean Intersectionで交差部分を残す設計。開いた建物面ではBooleanが破綻しうるため、平面クリップ＋境界ループのキャップ生成を代替候補とする（成功可否は**要検証**）。建物の重心選別だけでは境界をまたぐ建物を切断できない。円形は円柱カッターによる次段階とする。
4. **断面・底面**：境界に厚みのある閉じた台座を作り、建物切断部と台座側面を区別する。断面には層状マテリアルを割り当てる設計。初回は白一色で厚みと閉じ方を検証し、地層色は次段階。CityGMLから地下の実測地層を生成できるとは扱わない。
5. **浮遊・静止画**：地区全体を親オブジェクトで持ち上げ、暗背景と斜俯瞰カメラで側面・底面を見せる。元の地表から離れたことを読める構図とし、同一カメラで「建物のみ／断面あり」を比較する。浮遊感の成立は**要検証**。
6. **再現**：入力・ツール版・コード版、境界／CRS／原点、素材、カメラ、照明・時刻、持ち上げ量、シード、レンダー設定をレシピとともに保存する。

## VMと実行方式

2026-11-05の確認で `which blender` と `command -v blender` は出力なし。**PATH上のBlender実行ファイルはない**。別ディレクトリへの手動配置は未探索（**要検証**）。VMは `x86_64`、作業領域の空きは約145GB。GPU有無・RAM・CPU性能は今回未計測（**要検証**）で、以下はCPUのみを前提とする設計。

| 選択肢 | 導入・資源の見積もり（すべて要検証） |
| --- | --- |
| aptパッケージ | OSリポジトリの版・依存関係・権限を確認後に検討。取得100〜500MB程度、導入後0.5〜2GB程度の概算。アドオン対応版との一致は要検証 |
| 公式Linux tarball | [Blender公式配布](https://www.blender.org/download/)から版固定する案。取得約300MB級（版により増減）、展開1〜2GB程度の概算。配布URL・実サイズ・共有ライブラリ依存は要検証 |
| データ・中間成果物 | 対象区全体の取得量は不明。ZIP・展開GML・変換メッシュ・blendを併存させるので、仮の作業枠10〜30GBを置き、HEADと展開後実測で更新（要検証）。空き容量だけではRAM適合を保証しない |

ヘッドレスはBlenderのバックグラウンド実行を使う案。CPU CyclesであればGPUなしの静止画検証を狙えるが、このVMの起動・依存・所要時間は**要検証**。初期設定案は1280×720、32 samples、デノイズ、1フレーム。数分〜数十分／枚は仮の目安（**要検証**）で、形状数による増大を測定する。

Eeveeは高速描画候補だが、GPU／グラフィックスコンテキストとヘッドレス対応条件に依存するため、CPUのみでの安定動作・速度は**要検証**。CyclesはCPUで計算量が重い代わりに今回の第一候補。SwiftShaderでブラウザの描画が動くことは、BlenderのEeveeやCyclesが動く根拠にならない。インストール・試験実行は今回実施していない。

## 工数・リスクと最小スパイク

S＝0.5〜2人時、M＝2〜4人時、L＝4〜8人時。以下は未実測の概算で**要検証**。転送待ち・レンダー待ちは人時と分ける。

| 工程 | 規模 | 主なリスクと打ち切り条件 |
| --- | --- | --- |
| データ特定・HEAD・利用条件確認 | S | 到達不可／対象年度不明なら取得せず保留 |
| Blender導入・CPU起動確認 | S | 無料・既存権限の範囲で成立しなければ保留 |
| 小メッシュ変換・1km抽出 | M | CRSずれ、LOD欠落、変換器互換性。4人時で通らなければ経路を再評価 |
| 切断・キャップ・台座 | L | 非多様体、穴、Boolean失敗。人工台座だけの結果を真の切断成功としない |
| 白素材・照明・1枚レンダー | M | RAM超過／計算時間。まず解像度・対象オブジェクトを減らして切り分ける |
| 再現・比較・記録 | S | 同条件比較ができなければクリエイティブ判定を保留 |

合計約9.5〜22人時（概算・**要検証**）。最初は4人時までで取り込みの可否を判断し、未解決のまま断面演出へ進まない。

**最小定義：「千代田1km四方、白素材、切断1回、静止画1枚」。** 1km四方の境界は取得後に固定し、境界をまたぐ建物が少なくとも1棟ある場所を選ぶ。新宿・円形・テクスチャ・動画・実地形の完全復元は後続とする。

成功基準を分ける。

- **技術**：実データの地区・年度・縮尺が確認できる。境界をまたぐ建物が実際に切れ、切断部と台座に明らかな穴・突き抜けがない。側面・底面を備えた地区が分離して描かれる。CPUで1枚を出力でき、レシピから再生成できる。目安の上限はレンダー60分／枚（提案、実測適合性は**要検証**）。
- **クリエイティブ**：ユーザーの目視で「暗所にある建物群」から「厚みを持つ浮遊した街」へ読みが改善する。同一構図の建物のみの対照を用意し、第一印象・都市らしさ・構図を分けて記録する。最小成果物は断面あり1枚、対照は比較用。未描画の現時点は**未確認**で採点しない。

## Go / No-Goの判断

| LIFT-LITEの目視結果 | Blender経路の扱い |
| --- | --- |
| 浮遊模型として成立 | 断面は完成度を上げる追加要素。LITEの構図・DOF改善を先行し、Blenderは後順位の小スパイク |
| 建物が暗所に並ぶだけで浮遊に見えない | 断面が不足要素という仮説の優先度を上げ、上記最小スパイクへ条件付きGo。断面で改善すること自体は要検証 |
| まだ目視していない（現在の記録） | クリエイティブ判断を保留。インストール・大量取得に進む前にユーザーのChromeでLITEを評価 |

LITEが失敗しても、無料のデータ／ツール経路が成立しない、4人時で取り込めない、切断工程の上限8人時で閉じた断面が作れない場合は、その経路をNo-Goまたは保留とする。再開条件は代替変換経路、小さい対象での成功、または工数見直し。技術成功後も、断面ありの画像が同条件比較で改善しなければ追加の量産・動画化を止め、EXP-001へ知見を戻す。
